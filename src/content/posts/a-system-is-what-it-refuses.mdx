Every design system I have been handed arrives as a catalogue. Here are the
colours, here are the type sizes, here are the spacing steps, here are the
components; and here, usually in an appendix, usually written last, are some
notes on when to reach for which. The catalogue is generous. It is also, within
about six months, useless — not because anyone violated it, but because
everyone followed it. A list of permitted moves does not narrow a design space.
It enumerates one, and an enumerated space is a space you can wander in
forever. The load-bearing part of a system is never the inventory of what is
available. It is the record of what has been ruled out, and the reason attached
to each entry.

This is not a preference about documentation tone. It is a claim about what a
constraint does, and there is a useful distinction to borrow
here.<Sidenote>Juarrero's terms are *context-free* and *context-sensitive*
constraint. I use "governing" and "enabling" because they are easier to say in
a code review, at the cost of some precision.</Sidenote> Some constraints
reduce the number of things you can do. Others change what the remaining
things mean, so that the parts start to compose instead of merely coexisting.
Both are restrictions. Only the second is generative, and a system built
entirely out of the first kind is a system that gets thinner every time it is
enforced.

## Two kinds of constraint

A governing constraint removes options and stops there. Every button is 44
pixels tall. Nothing composes differently afterwards; there is simply less to
choose from. These are worth having — most accessibility floors are exactly
this shape — but they are inert. You can add a hundred of them and the system
will not have become more capable, only smaller.

An enabling constraint removes options *and creates a relation between the
ones left*. The rule in this project that colour may appear only where it
carries information is not a restriction on the palette; the palette is
untouched. It is a rule about what colour is *for*, and the moment it holds,
a coloured element becomes readable as a signal rather than as
decoration.<Sidenote>Which is why the rule has to be absolute to work at all.
One decorative use of the accent and every other use degrades to "possibly
decorative" — the reader has no way to tell the two apart from the
inside.</Sidenote> The constraint manufactures a meaning that did not exist
before it. Fewer moves, more expression.

| | Governing | Enabling |
| --- | --- | --- |
| Removes options | yes | yes |
| Creates relations | no | yes |
| Adding more | shrinks the system | deepens it |
| Failure mode | accumulates into paralysis | erodes silently on the first exception |

The failure modes matter more than the definitions. Governing constraints fail
loudly and additively: you end up with four hundred rules, a linter nobody can
turn off, and a team that has stopped proposing anything. Enabling constraints
fail quietly, and they fail all at once. There is no gradual decline from a
rule that holds to a rule that mostly holds.

## The fourth accent

This site's token file allows three accent colours. One is permitted in
running text — links, focus states, the single load-bearing element in a
diagram. The other two may appear inside diagrams and nowhere else. Then it
says this:

> There is no fourth accent, and adding one is not the fix. If a diagram needs
> a fourth category, THE DIAGRAM IS WRONG — split it into two diagrams.

The interesting clause is the second one. A governing version of this rule
would stop at "there is no fourth accent", and the first time someone had four
categories to draw they would either add a colour or give up on the rule, and
in both cases the rule would have contributed nothing except
friction.<Sidenote>The third option — draw the fourth category in a dashed
stroke instead — is worse, because it looks like compliance. The prohibition
survives and the thing it was protecting does not.</Sidenote> What makes it
enabling is that it converts a shortage into a diagnosis. Wanting a fourth
colour is now *information*: it means the diagram is carrying two arguments,
and the fix is upstream of the palette entirely.

Alexander made the general version of this point sixty years ago, in the
context of buildings. You cannot specify good fit positively — there is no
list of properties whose presence makes a design correct. What you can do is
enumerate the ways a design fails to fit, and treat the design as whatever
survives the enumeration. A system of prohibitions is that enumeration, kept
where the work happens.

## A prohibition has to name the failure

Which sets the standard for how they are written. "Do not use more than three
colours" is a rule; it can be obeyed and learned nothing from. "A fourth
category means the diagram is doing two jobs" is a diagnosis, and a reader who
hits it is better at diagrams afterwards.

The same test applies to every prohibition in the file. Sidenotes may not
appear in a note, because a note has no margin column for one to live in.
Containers have a minimum height and are never shrink-wrapped, because
whitespace collecting at the foot of a short sheet is the point rather than
the defect.<Sidenote>This one I got wrong twice before writing it down, both
times by "fixing" the empty space at the bottom of a nearly-empty
container.</Sidenote> Each states the failure, not just the boundary. That is
what makes them survivable: a rule whose reason is recorded can be argued with
and, when the reason expires, retired. A rule without one can only be
inherited or broken.

Note the asymmetry in cost. Writing the reason takes a sentence at the moment
you already have it in your head. Recovering it eighteen months later takes an
afternoon of archaeology, and usually ends with someone deciding the rule was
arbitrary — which, undocumented, it now effectively is.

## What prohibitions cost

They have to be held by someone, and people are bad at holding
things.<Sidenote>Ostrom's work on long-lived commons institutions is
instructive here: the durable ones share a small set of features, and among
them are boundaries the participants can actually perceive and consequences
that arrive early and in proportion.</Sidenote> This is the argument for
moving prohibitions out of prose and into whatever fails the build. In this
project a note that declares a `deck` does not render oddly; it does not
render. The content schema rejects the frontmatter and the build stops, with
a message that explains that notes are filed sheets rather than published
arguments and carry a document header instead of a
standfirst.<Sidenote>The schema is also where the reason gets its best
audience. Nobody reads a style guide at the moment of writing frontmatter;
everybody reads the error that just stopped their build.</Sidenote>

That is the same prohibition as the one in the prose, moved somewhere it does
not depend on anyone remembering it. The prose version teaches; the schema
version holds. A system needs both, and the common mistake is shipping only
the first and calling the result a design system.

## The test

Brand's account of buildings has them changing at several speeds at once, the
fast layers rearranging themselves inside slow ones that barely move. Design
systems have the same structure, and the prohibitions are the slow layer. The
components will be rewritten; the colours will be retuned; the prohibitions,
if they are any good, will still be true after both.

So the test is not whether a system is well documented, well tokenised, or
comprehensively adopted. It is whether you can violate it without noticing.
If nothing in the system pushes back — no build failure, no rule whose reason
you would have to argue with, nothing that makes a wrong move feel wrong
before it ships — then what you have is not a system. It is a mood board with
a package name, and it will be replaced within the year by another one.
